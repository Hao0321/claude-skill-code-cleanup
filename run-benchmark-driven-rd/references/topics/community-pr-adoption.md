# Community adoption experiments

Use for community PR adoption or retrospective training. The reciprocal [Cleanup card](../../../code-cleanup-helper/references/topics/community-pr-audit.md) owns source/inventory audit rules. Keep project-specific preferences and complete incident histories local.

- `rd.community.product-fit`: freeze the user's platform, workflow and quality constraints before experiments. Scope rejection can be decisive even when a candidate works. Each project declares its own constraints; one desktop product does not define policy for other products.
- `rd.community.benefit`: classify functional, safety and maintenance benefit; declare a task-shaped baseline and decision threshold. Test complete state/persistence/output flows when claimed. Unit counts, real-time recording or a synthetic output cannot prove native parity, human quality or real-world speed.
- `rd.community.repair-boundary`: preserve every actual failed attempt and classify its cause before retrying. Correct observed runner imports, guide selectors, prerequisites and edition configuration. Supply real dependencies for Windows alias fixtures and restore environment changes. Fake payloads, relaxed rejection controls or a different local candidate cannot turn an original-head failure into PASS.
- `rd.community.learning-closeout`: retain immutable raw attempts and corrections in `.rd/`; shared cards contain bounded, sanitized rules with one owner. Preserve verified harnesses and actual edition manifests before retiring owned rebuildable caches. Read real field locations rather than guessing a common schema. After authorized skill edits, capture/verify a new revision while retaining the audit's original revision proof.

Use the existing learning gate for provenance/promotion state. Structural and regression checks validate the stated dimensions; behavioral improvement remains unmeasured until an independent task replay supports it.
