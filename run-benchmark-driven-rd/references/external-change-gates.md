## 1. Why this gate exists

External writes are not ordinary implementation details. A technically successful API call can still mutate the wrong repository, account, database, automation, domain, release, or deployment.

Separate four questions:

1. **Should anything change?** User intent and scope.
2. **Which exact resource changes?** Canonical-target resolution.
3. **Can the final action complete?** Technical authorization and interaction surface.
4. **Did only the intended state change?** Authoritative postconditions.

Do not start writing after answering only one or two of them.

## 2. Canonical-target discovery

Before create, rename, publish, transfer, archive, or delete:

1. Identify the account, owner, organization, region, and service.
2. Inventory existing resources in that namespace with an authoritative list/search API or CLI.
3. Normalize likely aliases: punctuation, prefixes such as `codex-skill-`, casing, historical names, URLs, remotes, and package identifiers.
4. Inspect creation date, last update, default branch, release/tag history, description, visibility, archive state, and local remotes.
5. Declare:
   - `canonical_survivor`: the resource whose history and public identity must remain;
   - `mutation_target`: the exact resource the current operation may change;
   - `alternatives_reviewed`: the similar resources that were checked and rejected.

Never use “`GET guessed-name` returned 404” as proof that no equivalent resource exists. For create operations, a namespace inventory and similar-name review are required even when the preferred name is available.

If local files are not connected to a remote, do not invent a new public identity until existing remote projects have been searched. If multiple candidates remain plausible, stop before external mutation.

## 3. Authorization and interaction preflight

User authorization and technical authorization are different evidence:

- **User authorization:** the user asked for this exact class of action and target.
- **Technical authorization:** the active credential/account has the exact required scope, role, sudo/2FA state, payment capability, and session.

Preflight the final operation, not only the first operation. Examples:

- GitHub `repo` permits ordinary repository writes but does not imply `delete_repo`.
- An authenticated browser may still require sudo mode, 2FA, email verification, or password re-entry for deletion.
- A deploy token may publish but not transfer or delete.

Record the user's available interaction surface:

| Availability | Allowed handoff |
|---|---|
| At desktop | Browser or CLI confirmation on that desktop |
| Remote with phone | Mobile device flow or direct mobile web confirmation |
| Unavailable | Defer the protected action; leave a safe reversible state |

Do not discover a desktop-only confirmation requirement after performing earlier mutations when the user is mobile-only. Device-flow codes must be generated by a process that remains alive until authorization is exchanged; a copied code from an exited process is not valid evidence.

Never ask the user to send passwords, 2FA codes, recovery codes, cookies, or access tokens. Prefer a first-party device flow where the user authorizes directly on the service.

## 4. Mutation sequence

Run `scripts/external_change_gate.py` against a frozen plan. Require `ALLOW` before the first external write.

Recommended sequence:

```text
inventory → resolve canonical target → preflight final authorization
→ choose interaction surface → dry-run/preview → mutate
→ authoritative postcondition check → record evidence
```

If the target changes during the workflow, invalidate the plan and rerun discovery. Do not reuse approval for a different resource.

Use explicit IDs and paths. Avoid broad globs, workspace roots, inherited default accounts, and name guesses. External mutation commands must show the owner and resource identifier.

## 5. Destructive deduplication

When an incorrect duplicate already exists:

1. Identify the older/canonical resource from history, releases, local remotes, documentation, and user intent.
2. Diff both resources without overwriting either.
3. Move only intended improvements into the canonical resource through a reviewable branch/PR or equivalent transaction.
4. Preserve the canonical history and version line; issue the next semantic version there.
5. Validate the canonical resource independently.
6. Archive/disable the duplicate as a reversible intermediate state and point it to the canonical resource.
7. Preflight permanent-deletion scope and sudo/2FA before promising deletion.
8. Delete only the duplicate's exact ID.
9. Verify the duplicate is absent and the canonical resource is still present and correct.

Deletion cannot be recovered through the normal workflow. If the service offers a recovery window, record it, but do not represent it as guaranteed rollback.

## 6. Postcondition verification

Use the authoritative API or service UI; local command success is insufficient.

For a repository deduplication, verify at minimum:

- deleted target returns authoritative not-found/absent state;
- canonical survivor still resolves;
- canonical visibility, default branch, latest commit, release/tag, license, and archive state match the plan;
- no same-name duplicate remains;
- local remotes and documentation point to the canonical survivor;
- temporary authorization is removed when it is no longer needed, if safe and requested by policy.

Keep raw commands/responses or stable evidence paths. Do not expose credentials in the evidence.

## 7. Incident-derived regression case

Use this task-shaped fixture to calibrate the gate:

```text
Existing namespace:
  owner/ai-short-drama
  created four days earlier
  public, MIT, main, release v1.0.0

Proposed action:
  create owner/codex-skill-ai-short-drama because one guessed lookup returned 404

User context:
  wants the existing skill updated and open-sourced
  later becomes mobile-only

Final cleanup:
  permanent repository deletion requires a scope not held by the existing write token
  browser deletion requires sudo/2FA
```

Expected detector results:

- **BLOCK create:** namespace inventory and similar-resource review are missing; the existing project is a plausible canonical survivor.
- **ALLOW canonical update only after resolution:** exact canonical repo, branch/PR, validation, privacy audit, and version progression are pinned.
- **BLOCK promised deletion before execution:** `delete_repo`/admin/sudo capability and mobile-completable authorization path are unverified.
- **ALLOW destructive cleanup only after recovery:** improvements exist in the canonical history, duplicate is the exact target, user authorized permanent deletion, technical authorization is ready, and target-absent plus survivor-present postconditions are declared.

This is a `target-resolution` failure followed by an `authorization` failure. Do not classify it as a naming preference or isolated CLI error.

Root causes to retain, not merely the symptoms:

- a guessed repository name and one lookup result were treated as a namespace inventory;
- creating a new resource was used as a fallback instead of resolving the user's existing canonical resource;
- ordinary `repo` write access was mistaken for proof that the later destructive action was executable;
- final-action scope, sudo/2FA, and user interaction constraints were checked only after promising the outcome;
- a desktop verification path was selected after the user had become mobile-only;
- completion was initially discussed before target-absent and survivor-present evidence existed.

Permanent invariant: discovery or authorization failure must never be converted into a new external identity. Block the mutation, preserve the canonical resource, and change only after the gate proves the exact target and end-to-end execution path.

## 8. Required evidence

Append to `.rd/EXTERNAL_CHANGES.md`:

```markdown
## <timestamp> — <operation id>

- Request: <user-authorized action>
- Namespace inventory: <command/API and result path>
- Canonical survivor: <stable ID/URL and evidence>
- Mutation target: <stable ID/URL and evidence>
- Similar resources reviewed: <list>
- Technical authorization: <scope/role/sudo status without secrets>
- User availability: desktop | mobile-only | unavailable
- Recovery/rollback: <plan or explicitly irreversible>
- Gate result: ALLOW | BLOCK
- Execution evidence: <command/API result path>
- Postconditions: <checks and results>
- Failure type: target-resolution | authorization | integration | ...
- Reusable rule: <one sentence>
```

Also append the attempt to `.rd/experiments/ledger.jsonl` and stable failure patterns to `.rd/FAILURES.md`.
